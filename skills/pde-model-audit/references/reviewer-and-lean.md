# 数学审稿与 Lean 核验

用于数学模型、证明、研究论文的逻辑审查；与数学严谨性参考配合。目标是找出第一处不成立或缺依据的推理，并提出保持研究对象的最小修正。不是给文章套统一章节，也不要求每个项目安装 Lean。

## 1. 定义与主张的依赖

先建立简短对应：主张位置 → 使用的对象/条件 → 所需引理或定理 → 实际证据 → 结论范围。
从首次使用追踪定义、量词、域、单位、测度、边界、初值及符号重用。附录或后文不能代替首次必要定义。
逐条核对：
- 输入给定与未知量是否混淆，条件是否足以闭合系统；
- 守恒是否推出耗散、有限矩阵元是否被当作连续有界性、有限阶可解是否被当作一致稳定；
- Lax–Milgram、inf-sup、Gronwall、比较原理、椭圆/抛物正则性等实际调用的每个条件是否满足；
- 分部积分、微分与积分/极限交换、非零分母、源点乘积、迹和点值是否有定义；
- “证明了”“观察到”“假设”“候选解释”是否与实际证据对应。

不能仅写“理论不足”。指出缺少的是哪个定义、可积性、边界迹、估计、紧性、唯一性、存在性、离散稳定常数或实现对应，给出要补的精确命题和顺序。

## 2. 审稿结论分级

- **错误**：给出反例、符号/单位矛盾或不合法步骤；说明影响的后续结论。
- **条件缺失**：结论在补充的明确假设下可能成立，说明如何核验实际模型是否满足。
- **证明缺口**：命题可能为真，但现有论证没有建立；指出所缺引理。
- **证据不足**：计算或引用不覆盖主张；说明需要什么独立验证。
- **表述问题**：逻辑已成立，但顺序、记号或定义妨碍理解；直接改。

按影响排序，不把未形式化误判为数学错误。复述定理或添加防御性文字不能替代修复。

## 3. Lean 在何时进入

用户要求形式化，或项目已有 Lean 工程且数学审查适合机器核验时，检查其当前 Lean/Lake、mathlib、固定依赖和已有验证入口。优先扩展已有工程。普通写作审查不自动安装大环境。
选择对论文主张有辨识力的命题：守恒、约束、反例、参数范围、积分或矩阵性质。只核验容易的代数时明确覆盖范围，不把定理数当作模型完成度。

### 命题一致性是首要门槛

对每个 Lean 定理核对：
- 定义是否就是原方程的对象，是否换了源核、空间、条件、标量域或离散对象；
- 量词与参数范围是否相同；
- 是否把目标或等价命题偷偷作为假设；有无循环依赖或不可能满足的前提；
- 连续积分是否退化成未说明的有限和，复数矩阵是否改成实标量；
- 解存在、可积性、独立性和可逆性是已证明还是显式假设；
- 只证明了局部符号/导数关系，还是确实得到全文声称的全局结论。

数学等价的编码可用，但必须解释对应；为让 Lean 通过而改变研究问题不可用。

### 运行与公理审计

使用工程的真实构建与验证命令。编译成功之后检查全部项目定理的 `#print axioms`，拒绝 `sorry`/`admit`、`sorryAx`、隐藏自定义公理和未经说明的证明绕过；标准基础公理通常包括 `propext`、`Classical.choice`、`Quot.sound`。
不要禁用错误/警告来宣称通过，也不要只作源文本搜索而不检查间接依赖。可信环境中标准 `decide` 与生成可核验项的 tactics 可用；原生判定或外部求解器的信任边界须另报。
记录 toolchain、依赖提交、源码/论文身份、命令、退出状态、公理日志和覆盖表。失败重跑不得继续展示过期的 passed 状态。

## 4. 交付与修正

输出“位置—主张—问题—依据—最小修正—状态”。对已修正文稿检查定义顺序、符号、公式和引用；重新编译并看页面。
对每个形式化成果给出论文公式/命题到 Lean 名称的对应、完整假设和未覆盖的部分。区分人工数学审查、Lean 内核检查、数值验证、物理解释。
未通过时先定位数学问题、编码问题、库缺失或环境问题。数学上无效的命题用反例说明；库缺失不作为命题错误证据。不要用最高阶数据、低残差或形式化的简单引理填补适定性和收敛证明。
数值实验转 numerical-experiment，异常定位转 numerical-diagnosis，文稿维护转 manuscript-maintenance；不擅自启动额外高阶计算。
